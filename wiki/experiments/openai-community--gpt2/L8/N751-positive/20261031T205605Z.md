The first model is easier to teach and the second is easier to debug, and the distance between them explains most of the confusion that new implementers run into. Start with the frame. Every frame carries a nine-octet header: a three-octet length field, a one-octet type field, a one-octet flags field, and a four-octet stream identifier. The length field counts the payload only, not the header, which is a detail that trips people up in exactly one place: when the payload is empty, the length is zero and the frame still occupies nine octets on the wire. A parser that assumes length means total size will emit a stream of garbage after the first empty frame and will spend an afternoon wondering why. Flow control is where the two windows come in. Each endpoint advertises an initial window size in its settings frame; the default is 65,535 octets, which dates to an era when that seemed like a generous amount of memory to reserve per connection. The sender may not have more than the advertised window in flight, and every data frame it sends decrements the window by the payload length. The receiver returns window update frames as it consumes data, adding credit back. Nothing about this mechanism guarantees fairness, and nothing guarantees that the sender will ever be allowed to send more than the initial window; if the application on the far side never reads, the window update never arrives and the sender blocks. That is a feature, not a bug: it is how the protocol pushes back on a producer that is faster than its consumer. The tricky part, and the one spec writers tend to bury in a footnote, is the interaction between flow control and stream priority. The window is per connection and per stream, and a stream can be blocked by either one, so a frame can be perfectly legal, well-formed, and still unable to move because some other stream on the same connection consumed the connection-level credit. Implementations that track only the stream window will appear to work under light load and will deadlock under heavy multiplexing, which is the sort of defect that only shows up in production, at the worst possible moment, after everyone has already gone home. There is also a subtlety around the settings handshake. The initial window applies until the peer acknowledges a settings frame that changes it, and the acknowledgement happens at the frame level, not the octet level, so there is a brief interval during which the sender is using the old window while the receiver believes the new one is in force.
